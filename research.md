# Задание 1. Исследование моделей и инфраструктуры

## Для кого и с какими ограничениями

Задачу ставит руководство R&D и CTO QuantumForge: им нужно сократить время на поиск по документации и подготовку к SOC 2.
Пользуются ботом разработчики (архитектурные решения, API, описание микросервисов), саппорт (типовые проблемы клиентов),
менеджеры и аналитики (регламенты), новички (онбординг) и GRC-команда (актуальные политики для аудита).

Из этого я вывел ограничения, которые влияют на выбор сильнее, чем качество модели:

- Компания в ЕС (Финляндия, Эстония), значит GDPR и требования к месту обработки данных. YandexGPT поэтому сразу
  отпадает: данные уходят в российскую юрисдикцию, для европейской компании с клиентами вроде ABB и Wärtsilä это
  неприемлемо по комплаенсу. Дальше в сравнении он только для полноты.
- Часть базы конфиденциальна: ~250 PDF-спецификаций заказных проектов клиентов (под NDA), политики SOC 2 и GRC,
  HR-регламенты. Эти документы нельзя отправлять во внешний API ни при индексации, ни в промпте.
- Остальное (README, ADR, API-документация, onboarding, Zendesk Guide) внутреннее, но без запретов на облачную
  обработку при договоре с zero data retention и обработкой в ЕС.
- Рабочий язык документации английский, вопросы будут задавать на английском, русском, финском и эстонском. Нужны
  многоязычные эмбеддинги.
- Компания уже живёт в AWS (EKS, RDS), своей железной инфраструктуры нет. Решение должно ложиться в EKS.

## Объём данных

Оценка, от которой считал стоимость и железо:

| Источник | Количество | Токенов (оценка) |
|---|---|---|
| Markdown/MDX в репозиториях | 18 000 файлов × ~1 500 | ~27 млн |
| Confluence | 3 000 страниц × ~2 000 | ~6 млн |
| PDF-спецификации | 250 × ~30 страниц × ~600 | ~4,5 млн |
| Итого | | ~38 млн токенов |

При чанках по ~400 токенов с перекрытием 15% выходит около 110 тыс. чанков. Прирост 400 страниц в месяц это
~0,8 млн токенов, то есть ~2 тыс. новых чанков в месяц. Нагрузку на бота взял такую: ~150 активных пользователей
по 10 вопросов в день, около 33 тыс. запросов в месяц. Запрос в RAG это ~3 000 входных токенов (system, примеры,
5 чанков, вопрос) и ~400 выходных.

## 1. LLM: локальные (Hugging Face) против облачных

| Критерий | Локальная (Qwen2.5-7B/14B, Llama 3.1 8B через vLLM) | OpenAI (GPT-4o-mini, GPT-4.1) | Anthropic Claude (Haiku, Sonnet) | YandexGPT |
|---|---|---|---|---|
| Качество ответов по контексту | Для RAG по найденным чанкам 7-14B хватает, но хуже держит инструкции, CoT и отказ «не знаю» | Высокое | Высокое, хорошо держит инструкции и отказы | Хорошее на русском, слабее на английском |
| Скорость | 30-60 токенов/с на L4, без сетевой задержки, зависит от загрузки GPU | 50-100 токенов/с, плюс сеть | Сопоставимо с OpenAI | Сопоставимо |
| Стоимость использования | Нет платы за токены | GPT-4o-mini ~$25 в месяц на нашу нагрузку, крупные модели в 10-20 раз дороже | Haiku 5.5 ~$17, Sonnet 5.5 ~$330, Opus 5.5 ~$660 в месяц | Не считал, отпадает по юрисдикции |
| Стоимость владения | GPU-нода ~$600 в месяц круглосуточно плюс время MLOps на обновление моделей | Почти ноль, платим за токены | Почти ноль | — |
| Развёртывание | vLLM или Ollama в EKS, GPU-нода, мониторинг, обновления весов | Ключ API | Ключ API | Ключ API |
| Конфиденциальность | Данные не покидают VPC | Уходят во внешний API (есть ZDR и обработка в ЕС по договору) | То же | Уходят в РФ |

Стоимость считал так: ~99 млн входных и ~13 млн выходных токенов в месяц, цены за 1 млн токенов вход/выход:
GPT-4o-mini $0.15/$0.60, Claude Haiku 5.5 $0.10/$0.50, Sonnet 5.5 $2/$10, Opus 5.5 $4/$20.

Вывод: облачная модель дешевле и лучше по качеству, локальная нужна только для конфиденциального контура. Поэтому
бот работает с LLM через OpenAI-совместимый API: адрес, модель и ключ задаются в конфигурации. Одна и та же цепочка
RAG ходит в облако для обычных документов и в vLLM внутри VPC для конфиденциальных, менять код не нужно.

## 2. Эмбеддинги: локальные Sentence-Transformers против OpenAI Embeddings

| Критерий | Локальные (intfloat/multilingual-e5-small, 384; multilingual-e5-base, 768) | OpenAI text-embedding-3-small (1536) / large (3072) |
|---|---|---|
| Скорость индексации | e5-small на 8 vCPU ~150 чанков/с, весь корпус ~15 минут; e5-base в 3 раза медленнее, на GPU быстрее в разы | Ограничена rate limit, весь корпус ~30-60 минут батчами |
| Качество поиска | e5 хорошо работает между языками (вопрос на русском, документ на английском), чуть хуже больших облачных моделей | Выше на английском, многоязычность хорошая |
| Стоимость использования | Ноль | Полная индексация ~$1 (small) или ~$5 (large), прирост копеечный |
| Стоимость владения | Модель 0,5-1 ГБ в образе, CPU хватает | Ноль |
| Конфиденциальность | Тексты не покидают контур | Все чанки, включая NDA-документы, уходят наружу |

Деньги здесь почти не важны, решает конфиденциальность: индексировать конфиденциальные PDF облачной моделью нельзя,
а держать два разных эмбеддера для двух контуров неудобно (запрос надо кодировать той же моделью, что и документы).
Выбираю локальную многоязычную модель для всего корпуса: `multilingual-e5-small` для пилота, `multilingual-e5-base`
для продакшна, если пилот покажет нехватку точности.

## 3. Векторные БД: ChromaDB против FAISS

| Критерий | FAISS | ChromaDB |
|---|---|---|
| Скорость поиска | Самая высокая, `IndexFlatIP` на 110 тыс. векторов меньше 10 мс, есть HNSW и IVF для миллионов | Чуть медленнее (HNSW внутри), для наших объёмов разница незаметна |
| Скорость индексации | Добавление векторов в память, мгновенно | Медленнее, пишет на диск с метаданными |
| Сложность внедрения | Библиотека в процессе бота, сервер не нужен | Тоже встраивается в процесс, есть режим клиент-сервер |
| Поддержка | Метаданные и фильтры пишем сами, удаление по id есть только через обёртку `IndexIDMap`, файлы индекса синхронизируем и бэкапим сами | Хранит метаданные, фильтры `where`, удаление по id из коробки |
| Удобство | Низкоуровневое API, всё вокруг индекса своё | Удобнее для Python и LangChain |
| Стоимость владения | Только память: 110 тыс. × 384 × 4 байта ≈ 170 МБ | Память и диск, при десятках миллионов векторов упирается в RAM |

Для бота в этом проекте беру FAISS. База маленькая, нужна скорость и автономность, docker-образ без лишних
сервисов. Метаданные храню простым JSON рядом с индексом, а для инкрементального обновления (задание 6) оборачиваю
индекс в `IndexIDMap2`, чтобы удалять чанки изменённых документов по id без полной пересборки.

Для продакшна QuantumForge FAISS упрётся в фильтры: класс конфиденциальности и роли (кто какие документы может видеть)
придётся проверять после поиска своим кодом, а метаданные, бэкапы и синхронизацию файлов индекса между репликами
бота поддерживать самим. Тогда переходить на Qdrant: фильтр по метаданным до ANN-поиска, хранение payload рядом с
вектором, снапшоты, свой оператор в Kubernetes. Chroma для продакшна не беру: по фильтрам она
закрывает то же, но на десятках миллионов векторов упирается в RAM, а Qdrant шардируется.

## 4. Конфигурация сервера

Цены ориентировочные (AWS, eu-north-1, on-demand), чтобы сравнить варианты между собой.

| Вариант | Состав | LLM | Стоимость в месяц | Минусы |
|---|---|---|---|---|
| A. Всё в облачном API | 1 нода 4 vCPU / 16 ГБ RAM без GPU: бот, эмбеддер, FAISS | Облачная (Claude Haiku 5.5 или GPT-4o-mini) | ~$150 нода + ~$20 токены | Конфиденциальные документы либо уходят наружу, либо их нет в базе |
| B. Всё локально, крупная модель | 1 GPU-нода 1× L40S 48 ГБ, 16 vCPU, 64 ГБ RAM | Qwen2.5-32B-Instruct (AWQ) через vLLM | ~$1 400 | Дорого, нужен MLOps, качество всё равно ниже облачных |
| C. Гибрид (выбран) | CPU-нода 8 vCPU / 32 ГБ RAM (бот, эмбеддер, векторная БД) + GPU-нода 1× L4 24 ГБ, 8 vCPU, 32 ГБ RAM | Облачная для обычных документов, Qwen2.5-7B или Llama 3.1 8B в vLLM для конфиденциальных | ~$300 CPU + ~$600 GPU + ~$25 токены | Две модели в эксплуатации, нужна маршрутизация по классу документа |
| D. Свой сервер в офисе | 1× RTX 6000 Ada 48 ГБ, 64 ГБ RAM | Локальная 32B | ~€12 000 разово | Компания облачная, железо некому обслуживать, нет отказоустойчивости |

Почему C. Конфиденциальные документы (NDA-спецификации, SOC 2, HR) обрабатываются только внутри VPC, при этом
обычные вопросы разработчиков и саппорта получают качество облачной модели. GPU-ноду можно поднимать в EKS по
расписанию (рабочие часы), тогда её стоимость падает примерно вдвое. Для пилота хватает варианта A на одной CPU-ноде:
база знаний тестовая и не конфиденциальная.

## Итог

- LLM через OpenAI-совместимый API, модель задаётся конфигурацией. На пилоте облачная Claude Haiku 5.5, в продакшне гибрид:
  облако для обычных документов, vLLM с 7-8B моделью в VPC для конфиденциальных.
- Эмбеддинги локальные: `intfloat/multilingual-e5-small` (384 измерения) на пилоте, при нехватке точности
  `multilingual-e5-base`. Документы при индексации не покидают контур.
- Векторная БД для бота FAISS (`IndexFlatIP` с нормализацией, то есть косинус, в обёртке `IndexIDMap2` для удаления по id): быстро, без отдельного сервиса,
  достаточно для пилота. При переходе в продакшн с фильтрами по ролям и классу конфиденциальности переезд на Qdrant.
- Сервер: для пилота 4 vCPU / 16 ГБ без GPU, для продакшна вариант C.
